# BPC C++ Core

This folder contains the C++17 core for the BPC algorithms used in the project:
dynamic segmentation, compartment feasibility resources, label pricing,
Gurobi-MIP pricing, column generation, branch-and-bound, and warm-start loading.

Implemented core modules:

- dynamic segmentation: mirrors `src/utility/dynamic_segmentation.py`,
  including independent height-based splits and fixed side-block splits.
- residual-profile label pricing: exact enumeration (`EX`), certified
  ordered-greedy generation (`D2`), hybrid conflict/ordered generation (`HYB`),
  reduced-cost bound, and D1 residual/quantity dominance.
- solver pricing: Gurobi MIP subproblems for both compartment BPC and full-wagon
  BPC. The wagon solver backend uses one full pricing MIP with binary `z_p`
  variables to choose the deck mode and load upper/lower components jointly.
- BPC driver: restricted master LP/IP, column generation, branch-and-bound,
  wagon columns, compartment columns, and deck-map constraints.
- cuts: optional rounded capacity cuts and separated 3-SR cuts in the master;
  their duals are passed into both label-pricing and solver-pricing reduced
  costs.
- `--warmstart-json PREFIX:PATH`: import `carriage_info.json` style solutions,
  revalidate every upper/lower compartment with the full profile evaluator, and
  add only feasible non-duplicate columns. If the imported columns cover demand,
  the solver first solves a restricted IP to install a warm-start incumbent.
- Gurobi master and pricing models use `--threads N`; the default is one thread
  for ablation comparability. Use `--threads 0` to leave Gurobi at its own
  default.

Main solver options:

- `--method wagon|compartment`
- `--pricing-backend label|solver`
- `--profile-generator-mode ex|d2|hyb` for the label backend
- `--threads N`
- `--max-columns-per-pricing N --max-columns-per-subproblem N`; for label
  pricing, nonpositive values mean no column-count limit in one CG update
- `--num-splits N --independent-mode-split true|false`
- `--component-length-perturbation-mm MM` for deterministic label-pricing
  tests with component-dependent loading lengths on a subset of car types
- `--warmstart-json PREFIX:PATH`

Build:

```bash
cd BPC_label_cpp
make
./bpc_label_smoke
./bpc_label_solver --instance ../data/Instance/m5c5 --method wagon --use-cuts true
./bpc_label_solver --instance ../data/Instance/m5c5 --method wagon --pricing-backend solver
./bpc_label_solver --instance ../data/Instance/m5c5 --method wagon \
  --warmstart-json compact:../result/tmp_cpp_compare/compact_m5c5/solver/carriage_info.json
```

`cmake` is not required; this environment currently has `c++` but not `cmake`.
On Windows servers, CMake is the preferred build path because it can use the
Visual Studio Build Tools compiler.

Comparison helper:

```bash
python3 scripts/compare_cpp_bpc.py --instances m5c5 --use-cuts --mip-gap 0
python3 scripts/compare_cpp_bpc.py --instances m5c5 --pricing-backend solver --use-cuts
```

Numerical batch experiments:

```bash
python3 src/utility/cpp_core_batch_experiments.py --date 2026-05-21 --generate
python3 src/utility/cpp_core_batch_experiments.py --date 2026-05-21 --run
```

The C++ core batch uses the 96 instances generated by
`src/utility/batch_experiments.py` and runs eight reported methods:

- `bi`
- `vns`
- `gurobi`
- `bpc_wagon_label`
- `bpc_wagon_solver`
- `bpc_compartment_label`
- `bpc_compartment_solver`
- `bpc_compartment_label_ex_bi_ws_no_cut`

The four accelerated BPC methods run with cuts enabled and with BI/VNS
warm-start columns. If the warm-start JSON files are missing, the script runs
`VNS_cpp/vns_solver` first. If the imported warm-start columns do not produce
an incumbent, the script fails in strict mode. The method
`bpc_compartment_label_ex_bi_ws_no_cut` is the explicit baseline:
compartment BPC, label pricing, `EX` profile generation, BI warm-start columns
only, and no cuts.

On Windows, use:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/run_cpp_core_batch_experiments.ps1 -DateTag 2026-05-21 -ParallelJobs 4
```

or:

```cmd
scripts\run_cpp_core_batch_experiments.cmd -DateTag 2026-05-21 -ParallelJobs 4
```

Fresh Windows server setup:

```powershell
# Run once in PowerShell, preferably as Administrator.
powershell -ExecutionPolicy Bypass -File scripts/setup_cpp_windows.ps1 -InstallAll

# Install Gurobi separately, activate the license, then open a new PowerShell.
# If GUROBI_HOME is not already set, pass the win64 folder explicitly.
powershell -ExecutionPolicy Bypass -File scripts/run_cpp_core_batch_experiments.ps1 `
  -DateTag 2026-05-21 `
  -ParallelJobs 4 `
  -TimeLimit 3600 `
  -MipGap 0.0001 `
  -GurobiHome "C:\gurobi1301\win64"
```

The run script automatically builds `VNS_cpp\vns_solver.exe` and
`BPC_label_cpp\bpc_label_solver.exe` if either executable is missing. To force
a rebuild, add `-BuildCpp`. The build script targets x64 by default, which is
the intended platform for the Gurobi Windows libraries:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build_cpp_tools.ps1 `
  -GurobiHome "C:\gurobi1301\win64" `
  -Architecture x64 `
  -Clean
```

Use `-Clean` after a failed CMake configure, especially if CMake previously
selected `ARM64` or another unintended platform.

Deployment note: a server does not need a C++ compiler to run the prebuilt
executables, but it must match the target OS/architecture and must have the
required runtime libraries. The BPC executable uses Gurobi for master LP/IP
models and solver pricing, so the server still needs a compatible Gurobi
runtime and license even when the C++ compiler is absent.
